STACKFALL — v1.0 Implementation Brief

Target: Anbernic RG503 / ROCKNIX / PortMaster
Language: C++17
Graphics and input: SDL2
Architecture: Native AArch64, deterministic gameplay core
Status: Specification complete; implementation pending

1. Product definition

STACKFALL is a single-player, offline, endless block-stacking game designed specifically for handheld controls.

A player moves and rotates falling geometric shapes to complete horizontal lines. Completed lines disappear, awarding points and increasing game speed. The game ends when the board fills beyond the allowed spawning area.

Version 1.0 will be fully playable, not just a technical demonstration.

Features included

* Seven tetromino shapes: I, O, T, S, Z, J, L
* 10 × 20 visible board with two hidden rows
* Smooth movement, rotation and wall kicks
* Seven-piece bag randomizer
* Hard drop and soft drop
* Hold piece and five upcoming pieces
* Ghost piece showing landing position
* Line clearing, scoring and increasing levels
* Title, controls, pause and game-over screens
* High-score persistence
* Procedural graphics and simple synthesized sounds
* Full controller support
* Standalone ROCKNIX installation

2. Core game mechanics

Board: 10 columns, 20 visible rows, two hidden rows.

Shapes: All seven standard four-block tetrominoes, with four orientation states each.

Rotation: Super Rotation System (SRS), with clockwise/counter-clockwise 90° turns and the appropriate wall-kick tables.

Randomizer: Shuffle seven distinct pieces into a bag, consume the bag, then reshuffle. Maintain five upcoming previews.

Gravity: Starts at one row every 48 simulation ticks and accelerates every ten cleared lines, reaching a maximum of one row per tick.

Locking: A grounded piece locks after 30 ticks. Valid grounded movement/rotation can reset that timer at most 15 times per piece.

Line clearing: Clear one through four completed rows simultaneously, shifting everything above them down.

Game over: Occurs on failed spawning or locking cells above the visible board.

Scoring

Event	Points
Single	100 × level
Double	300 × level
Triple	500 × level
Four-line clear	800 × level
Soft drop	1 per cell
Hard drop	2 per cell

No T-spin, combo or back-to-back bonuses in the first release.

3. Controller layout

RG503 input	Action
D-pad Left / Right	Move
D-pad Down	Soft drop
A	Rotate clockwise
B	Rotate counter-clockwise
X	Hard drop
Y / L1	Hold
Start	Pause / resume

Controller mappings will be verified on the physical RG503. Keyboard input will be supported for desktop testing.

Horizontal movement uses 10-tick delayed auto-shift and a two-tick repeat interval.

4. Visual design

* 960 × 544 native logical screen
* 24 × 24 pixel cells
* 240 × 480 pixel board
* Board origin at (360, 32)
* Hold panel on the left
* Five upcoming-piece previews and scoring on the right
* Dark background with high-contrast geometric blocks
* No sprites, texture files, image assets or external font files
* All text drawn from a source-defined 5 × 7 pixel-glyph table

SDL2 will draw everything using filled rectangles and lines.

5. Data model

Board: A 22-element array of 16-bit integer row masks. Each row uses ten occupancy bits. A parallel 22 × 10 byte array records block types for coloring.

Piece: Identity, rotation state and integer position.

Game state: Board, active piece, held piece, next-piece queue, randomizer state, score, level, cleared lines, gravity timer, lock timer and current screen.

Input: A small tick-indexed structure containing held directions and discrete button-press events.

Simulation: Pure C++ code, entirely independent from SDL2.

Rendering: Read-only access to the game state.

Persistence: Versioned high-score data stored in the application’s writable configuration folder.

6. Main architecture

The source will be divided into two layers.

Core layer (no SDL dependency)

* Tetromino definitions and SRS rotation tables
* Board and collision logic
* Randomizer and next queue
* Gravity and movement rules
* Lock delay and line clearing
* Scoring and levels
* Game state machine
* Deterministic testing

Platform layer (SDL2)

* Window and renderer
* RG503 controller and desktop keyboard
* Fixed-step application loop
* Procedural board/UI rendering
* Audio initialization and simple synthesized effects
* Filesystem persistence
* ROCKNIX-specific launching

The build system will expose separate targets for the game executable and the headless test runner.

7. Development milestones

M0 — Project foundation

Create the CMake project, portable C++ core library, test runner, SDL2 initialization and a working desktop window. Verify controller discovery and clean shutdown.

M1 — Mathematical game engine

Implement the seven shapes, four orientations, SRS rotations, board bitmasks, collision detection, seven-bag queue, gravity, hold, lock delay, scoring, ghost position and line clears.

The complete mathematical engine must pass headless tests before visual development begins.

M2 — First playable desktop build

Add rendering, controller/keyboard input, fixed 60 Hz gameplay, title screen, active gameplay, pause and game-over screens.

M3 — Complete gameplay and persistence

Add high scores, UI polish, audio feedback, input-repeat tuning, error handling and deterministic regression tests.

M4 — Native RG503 build

Compile for ARM64 in a PortMaster-compatible environment. Create the shell launcher, initialize SDL controllers, validate display output and test on the actual device.

M5 — Release

Create a ready-to-run PortMaster package with metadata, gameplay screenshot, README, licenses and reproducible build instructions.

8. Required test coverage

The test suite must verify shape orientation, exact four-cell occupancy, board boundaries, SRS kicks, settled-piece collisions, all four line-clear quantities, scoring, seven-bag correctness, hold restrictions, hard-drop landing, gravity timing, pause behavior, lock delay and top-out.

It must also verify that identical seeds and input sequences produce identical game outcomes and that high scores survive application restarts.

9. Release acceptance

Version 1.0 is complete when the game launches from ROCKNIX Ports, works entirely from the RG503 buttons, displays correctly at native resolution, plays full sessions at a stable targeted 60 FPS, saves records, survives repeated restarts, and exits cleanly.

No placeholder gameplay systems or manual keyboard configuration should be required on the handheld.

10. Immediate coding priority

The first implementation should produce:

1. The complete seven-shape definition table.
2. SRS orientation and wall-kick functions.
3. Bitmask board representation.
4. Pure mathematical collision detection.
5. Automated tests for each shape and rotation.

Only after these pass do we begin rendering the game in SDL2.

Guiding principle: The rules must be correct independently of the graphics, and the handheld must run exactly the same simulation as the desktop build.

What we’ll build first

Our first coding deliverable is a headless game engine that knows the seven shapes, rotates them correctly, detects collisions, and clears rows. That gives us a dependable mathematical foundation before we introduce SDL2.

The hardware target and native porting approach are grounded in the official ROCKNIX RG503 documentation⁠￼ and PortMaster packaging guide⁠￼. The rotation specification uses canonical SRS kick tables⁠￼. ROCKNIX Wiki +2

The v1.0 scope is now defined. The logical next step is M0 + M1: a real CMake/C++ repository with source files and automated tests that we can compile and progressively expand into the final handheld game.
